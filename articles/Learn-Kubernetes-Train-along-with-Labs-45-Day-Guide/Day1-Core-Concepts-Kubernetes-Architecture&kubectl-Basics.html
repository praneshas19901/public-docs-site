📋 Task 1: Cluster Setup & Pod Deployment

You can create this directly in your terminal using a single YAML manifest file, which is the standard practice for Kubernetes administration.

Step-by-Step Implementation

⏱️ Estimated Time: 1 min

1. Create the Namespace

Create the dedicated namespace for your lab workloads.

kubectl create namespace lab-workloads
  • Verification: Run kubectl get namespace lab-workloads and confirm it shows status Active.
⏱️ Estimated Time: 2 min

2. Create the Pod Manifest File

Create a YAML file named pod-lab.yaml containing the pod definition with resource limits, requests, and the HTTP liveness probe:

cat <<EOF > pod-lab.yaml
apiVersion: v1
kind: Pod
metadata:
  name: web-app
  namespace: lab-workloads
  labels:
    app: web-app
spec:
  containers:
  - name: nginx
    image: nginx:alpine
    resources:
      requests:
        cpu: "100m"
        memory: "64Mi"
      limits:
        cpu: "250m"
        memory: "128Mi"
    livenessProbe:
      httpGet:
        path: /
        port: 80
      initialDelaySeconds: 5
EOF
  • Verification: Run cat pod-lab.yaml to confirm the contents were written correctly.
⏱️ Estimated Time: 1 min

3. Deploy the Pod

Apply the manifest file to your cluster.

kubectl apply -f pod-lab.yaml
  • Verification: The output will confirm pod/web-app created.
⏱️ Estimated Time: 1 min

4. Verify Pod Status and Probe Configuration

Check that the pod successfully transitions to the Running state and inspect its details:

kubectl get pods -n lab-workloads -o wide

To verify that the resource requests, limits, and liveness probe are correctly active, run:

kubectl describe pod web-app -n lab-workloads
  • Verification: Look for Liveness: http-get http://:80/ delay=5s timeout=1s period=10s #success=1 #failure=3 and confirm the pod status is Running.

💡 PRO TIP: Understanding Automatic Service Account Mounts

In describe output you see:
Mounts: /var/run/secrets/kubernetes.io/serviceaccount from kube-api-access-cvx96 (ro)

Every Kubernetes Pod automatically receives a Service Account token mounted into its filesystem. This is what that specific mount is doing:

  • What it is: Kubernetes automatically creates a service account (named default unless specified otherwise) for every namespace and generates a short-lived authentication token, a Certificate Authority (ca.crt), and the cluster's namespace metadata.
  • Where it lives: It gets mounted dynamically into every container inside the pod at /var/run/secrets/kubernetes.io/serviceaccount as read-only (ro).
  • What it's used for: It allows applications running inside the container to securely authenticate and talk back to the Kubernetes API server (e.g., if your app needs to query cluster resources, create other pods, or watch configuration maps) without you having to manually embed credentials or passwords inside your container image.

If your application doesn't interact with the Kubernetes API, it simply ignores this directory.

🔍 Task 2: Cluster Inspection & Troubleshooting

Here are the exact kubectl commands to complete Task 1.2 (Cluster Inspection & Troubleshooting), along with what to look for in the output.

Step-by-Step Commands for Task 2

  • Verification: All system pods (like etcd-arm64-cluster, kube-apiserver-arm64-cluster, and kube-proxy) should display a status of Running with 1/1 ready containers.

📊 Deep-Dive Node Inspection Analysis

Here's a field-by-field breakdown of your kubectl get nodes -o wide output:

Field Value Explanation
NAME arm64-cluster-control-plane The node's hostname. This is a Kind (Kubernetes IN Docker) cluster named arm64-cluster. The suffix -control-plane is Kind's default naming for the control-plane node. The arm64 prefix tells you it's running on an ARM64 machine (Apple Silicon, Graviton, or similar).
STATUS Ready The kubelet has passed all health checks (sufficient memory, disk, PID, network). The node is schedulable and can accept pods.
ROLES control-plane This node runs the API server, scheduler, controller-manager, and etcd. Kind's default single-node cluster has only this one node. In production you'd also see worker nodes with role <none>. Kind control-plane nodes carry a taint (node-role.kubernetes.io/control-plane:NoSchedule) that prevents regular pods from scheduling there unless you explicitly tolerate it.
AGE 3d23h The node registered with the cluster ~4 days ago (3 days, 23 hours).
VERSION v1.29.2 The kubelet/Kubernetes version. ⚠️ Kubernetes 1.29 reached EOL on Feb 28, 2025 — it no longer receives security patches. You should upgrade (e.g., kind create cluster --image kindest/node:v1.34.x).
INTERNAL-IP 172.18.0.2 The IP on Docker's bridge network. Since Kind runs each node as a Docker container, this is the container's internal IP, not a real network address. It's only reachable from the host and other containers on the same Docker network.
EXTERNAL-IP <none> No public/external IP. Completely expected for a local Kind cluster — it has no internet-facing address.
OS-IMAGE Debian GNU/Linux 12 (bookworm) The container image inside the Kind node (not your host OS). Kind's default node images are Debian-based. This is what runs inside the Docker container that is the Kubernetes node.
KERNEL-VERSION 7.0.0-1013-oracle The host kernel (the VM/machine running Docker), not the container's. The oracle flavor means your host is an Oracle Cloud Infrastructure (OCI) VM. Kernel 7.0.0 was released upstream on April 12, 2026; -1013 is the 13th patch in that series. This is a very recent kernel.
CONTAINER-RUNTIME containerd://1.7.13 The container runtime inside the node is containerd v1.7.13 (released July 2024, updated runc to fix CVE-2024-21626). ⚠️ containerd 1.7 reached end-of-life on September 30, 2026 — no more security patches. If you upgrade the cluster, the new Kind image will ship containerd 2.x.

📌 Key Takeaways

  • It's a single-node Kind cluster on an ARM64 OCI VM — fine for local dev/testing, not for production.
  • Both Kubernetes 1.29 and containerd 1.7 are EOL. If this is more than a throwaway experiment, recreate the cluster with a newer image: 
    kind delete cluster --name arm64-cluster
kind create cluster --name arm64-cluster --image kindest/node:v1.34.2

🕵️ The Restart — Mystery Solved

This is the important part:

State:          Running
  Started:      Wed, 11 Nov 2026 03:37:21 +0000
Last State:     Terminated
  Reason:       Unknown
  Exit Code:    255
  Started:      Sat, 07 Nov 2026 04:53:06 +0000
  Finished:     Wed, 11 Nov 2026 03:37:17 +0000
  • The previous container ran from Nov 7 04:53 to Nov 11 03:37:17 (~3 days 23 hours).
  • It exited with code 255, reason "Unknown" — this means the process was killed externally (SIGKILL) rather than exiting cleanly. The container runtime couldn't capture a graceful exit.
  • The new container started 4 seconds later at 03:37:21.

What happened: The Docker container (your Kind node) was stopped/restarted at 03:37:17 UTC today. When the container stops, all processes inside die instantly (hence 255/Unknown). When it restarts, the kubelet re-runs the static pod manifest, and etcd comes back up. This is completely normal for Kind — it's not an etcd crash.

This also explains the 1 (87m ago) you saw in kubectl get pods — 87 minutes before you ran that command ≈ 03:37 UTC.

Flag Meaning
--data-dir=/var/lib/etcd Where etcd stores its data (rocksdb/bolt files). Mounted from the host.

--snapshot-count=10000 Take a snapshot every 10,000 compactions. Prevents the WAL from growing unbounded.
--experimental-initial-corrupt-check=true On startup, verify data integrity before serving. If corrupted, etcd refuses to start (safer than serving bad data).
--experimental-watch-progress-notify-interval=5s Send keepalive notifications to watchers every 5s even if no data changed. Prevents watchers from timing out on quiet clusters.
--client-cert-auth=true / --peer-client-cert-auth=true TLS mutual authentication for both client and peer connections.
--trusted-ca-file / --peer-trusted-ca-file CA bundle for verifying certificates.

Probes Configuration

Probe What it does
Startup GET http://127.0.0.1:2381/health?serializable=false every 10s, up to 24 tries (240s max). Gives etcd time to recover from a snapshot on boot before the liveness probe starts.
Liveness GET http://127.0.0.1:2381/health?exclude=NOSPACE&serializable=true every 10s, 8 failures = kill. The exclude=NOSPACE means "don't fail the probe just because the disk is full" (that's a separate condition). If etcd stops responding, the kubelet restarts the container.

📌 Note:

Both probes hit the metrics endpoint (port 2381), not the client port (2379). This is intentional — the health check shouldn't consume a client connection slot.

Volume Configurations

Volume Type Path Purpose
etcd-certs HostPath /etc/kubernetes/pki/etcd TLS certs/keys for etcd. DirectoryOrCreate means if it doesn't exist, create an empty dir (won't fail the pod).
etcd-data HostPath /var/lib/etcd The actual database. This is why etcd is a static pod with HostPath — the data must survive container restarts. If this were an emptyDir, etcd would lose all cluster state on restart.

Quality of Service (QoS) Class

Burstable — because it has resource requests (100m CPU, 100Mi memory) but no limits. The kubelet guarantees at least 100m/100Mi but allows etcd to use more if the node has headroom. It will be the last to be evicted under memory pressure (thanks to the priority class), but the QoS class itself just determines eviction ordering within the same priority.

💡 TL;DR:

Everything is healthy. The single restart was caused by the Docker container (node) being restarted today at 03:37 UTC — not by an etcd failure. The Exit Code: 255 / Reason: Unknown is the fingerprint of an external kill, which is exactly what you'd expect when the container itself is stopped.
